1 Overview

Builders populates a Minecraft world with AI-minded "Builder" folk — Citizens NPCs that wear real player skins and live, work, and build in towns that coexist with vanilla villages. Its centerpiece is an autonomous recruit → quest → completion loop: an external AI planner watches each online player's real advancement progress, sends a free Builder to physically walk up and offer a progression-appropriate quest, forms a party when the player accepts, and closes the quest the instant the player earns the matching vanilla advancement. Around that core sit the project's newest systems — an admin "Director" control console that interrogates an operator in chat and then, behind a strict confirm-gate, unleashes area-scoped disasters (zombie outbreaks, wildfires, storm-floods, meteors); fixed Builder personalities that color how each NPC speaks and whether it fights or flees; and player ⇄ Builder proximity chat where simply talking near a Builder gets an in-character reply. Every one of these subsystems is written in a different language by a different agent, and none of them ever calls another directly: they meet only in SpacetimeDB state.

The core loop

Planner picks a frontier quest → Builder walks to the player → offer → accept → complete the real advancement → party disbands, memory written.

Builder Life

Jobs, beds, a work-stealing build queue, and combat — Builders construct themed structures block-by-block and defend themselves.

The Director spec / building

Chat-driven admin console → confirm-gated actions → live disasters; only in-area Builders warn players, flavored by personality.

2 System architecture

Four programs orbit one hub. The Paper plugin reaches SpacetimeDB over the plain HTTP API (reducer calls + SQL reads); the worker and dashboard use the TypeScript SDK over WebSocket (live subscriptions + reducer calls). No program holds another's concerns, and no program has a socket to any other program — the database is the only wire.

FORCING CONSTRAINT 1 No Java SDK

SpacetimeDB has no Java client SDK, so the Paper plugin talks to the database over the raw HTTP API — POST /v1/database/builders-rpg/call/<reducer> for fire-and-forget writes and POST …/sql for blocking reads (parsed from SATS-JSON off the main thread). The entire DB connection is one file, Stdb.java.

FORCING CONSTRAINT 2 Reducers can't do I/O

Reducers run inside the database, sandboxed and deterministic — no network, files, clocks, or randomness. The LLM therefore cannot live in a reducer. It lives in an external worker that subscribes to the database and reacts to state changes, writing its decisions back through reducers. This is what makes "the AI reacts to the database" literally true.

3 The four programs

Each program is a clean slice of responsibility. The body has no intelligence; the bus has no I/O; the brain has no rendering; the window has no game logic. They share state, never code.

⚒ The Body Java · Paper 1.21.10

plugin/src/main/java/dev/builders/

Holds no intelligence. It streams game state to SpacetimeDB and executes whatever the brain (or a confirmed admin action) writes back. Citizens NPCs embody Builders with real player skins. Stdb.java is the entire DB connection. Game events become reducer calls (GameListeners: join/quit, advancements, NPC right-click). Background pollers read command queues on async threads, then hop to the main thread to act — DirectivePoller (story directives), BuildSystem (build-job queue), JobMechanics (job actions + universal combat), BuilderLife (beds / sleep / worksite movement), plus the new AdminExecutorspec / building and ScenarioEnginespec / building.

Writes (reducers)

Why it holds nothing else: it never decides what should happen — it can't reach the LLM, and it only reads the database. It is a pure actuator + sensor.

💾 The Shared World / Brain-Bus TypeScript · SpacetimeDB 2.4.1

stdb/spacetimedb/spacetimedb/src/index.ts

A relational database that is also the server — a WebAssembly module, no traditional game-server layer. It defines 16 public tables and the reducers that are the only way to write them. All tables are public: true so the worker and dashboard can subscribe and the plugin can read anonymously over HTTP. Reducers run transactionally and deterministically: either an entire change lands or none of it does. Players never connect here directly, so rows are keyed by explicit ids (player UUID strings, Citizens NPC ids) rather than ctx.sender.

Reads
its own tables (inside reducers)
Writes
its own tables (reducers only) · broadcasts every change to subscribers in real time

Why it holds nothing else: it can't render, can't call an LLM, can't touch Minecraft. It is the shared truth — the meeting point and the rule engine, nothing more.

🧠 The Brain / Mind Node · TypeScript SDK

worker/src/

Connects with the official SpacetimeDB TS SDK, subscribes to all tables, and runs reactive loops: plannerTick (∼20s — recruit players to frontier quests), builderTick + jobs.ts (∼12s — autonomous Builder life: assign jobs/beds/tools, drive the state machine, enqueue builds, restock, gossip, encourage), and the new director loopspec / building (admin-console LLM, ∼4s) and player chat loopspec / building. All "thinking" is gated to Builders near an online player (loaded chunks). llm.ts is OpenAI-compatible via the Kilo Gateway with a deterministic mock fallback — with no API key the whole system still runs, fully offline.

Why it holds nothing else: it never touches Minecraft or renders UI — it observes state and proposes/decides. It is pure cognition, expressed as reducer calls.

5 Reducers = the rule engine

Two rules that make half-states impossible

ATOMIC CAP request_recruitment

In one transaction the reducer checks the player exists, is not already partied, is under the difficulty cap (easy 2 / med 4 / hard 5 per phase), and has no duplicate pending offer — then increments the budget and inserts the quest + directive. If any check fails it throws and the whole thing aborts: no budget burned, no orphan quest. The worker pre-checks the same caps to save LLM calls, but the reducer is the source of truth — two simultaneous recruit attempts can never both win.

CONFIRM-GATE propose → confirm → execute

The Director only ever writes admin_action.status='pending' (via propose_action). The only reducer that can flip it to 'confirmed' is confirm_action, called by a human clicking Confirm. The plugin's AdminExecutor polls strictly WHERE status='confirmed'. There is no code path from pending to execution — the gate is structural, not advisory. Reject moves pending/confirmed → rejected and nothing runs.

7 LLM strategy

One OpenAI-compatible client (worker/src/llm.ts) serves every loop through the Kilo Gateway with model google/gemini-3.5-flash. The key dial is reasoning effort: HIGH where a real decision is being made (the planner, the Director), LOW where snappy one-liners matter (dialogue). If no API key is present, every helper returns a deterministic, theme-appropriate mock — the whole system runs fully offline and demo-safe.

GOTCHA, handled Reasoning eats the token budget

Reasoning models spend completion tokens on hidden thinking before the visible answer (∼680 thinking tokens just to write one invite sentence). Too small a budget and the answer comes back empty — a silent mock fallback. The planner/Director therefore get a generous 2048-token budget. The gateway returns the hidden thinking in a separate reasoning field, never in message.content, so parsing stays clean.

8 Why SpacetimeDB was the right choice

SpacetimeDB didn't just store data — it shaped the whole architecture, and most of the design's elegance falls directly out of its properties. The two constraints it imposes (no Java SDK; no I/O in reducers) turned out to bless the design rather than burden it.

The database is the server

Application logic is uploaded into the database as a WebAssembly module — there is no separate web/game-server tier to write, deploy, or scale. Modules are hot-swappable: republish without disconnecting clients. We never wrote a "server"; we wrote tables and reducers.

Reducers are a transactional rule engine

Atomic caps (request_recruitment) and the confirm-gate (propose→confirm→execute) mean no half-states and no race conditions: a recruit either fully lands or fully aborts; an action either is confirmed or cannot run. The rules live in one place that every client shares — they can't drift between plugin, worker, and dashboard.

Real-time subscriptions are the backbone

The worker and dashboard simply react to state changes via subscribeToAllTables + onInsert/onUpdate/onDelete. That is the clean "the AI reacts to the database" story made literal — and it hands us a live, judge-facing dashboard essentially for free.

One shared world

A single shared state gives multiplayer for free, and Builder memory is durable — it survives server restarts because it lives in the database, not the Minecraft world save. Restart Paper and the Builders still remember who they quested with.

Radical decoupling → multi-language, parallel dev

Java plugin, TS worker, and React dashboard coordinate only through SpacetimeDB state. That is exactly what let the team build subsystems (Builder Life; the Director; personalities; player chat) with independent parallel agents that never touched each other's code — they agreed on tables and reducers, then went heads-down.

HTTP for the body, SDK for the rest

The plugin needs no SDK — the HTTP API (/call + /sql) is enough. The worker and dashboard get the rich SDK with live subscriptions. Public tables + anonymous access keep the local/demo trust model dead simple: the only writers are the trusted backends.

Patterns it made trivial

work-stealing build_job queue (builder_id=0 → claim) brain→body story_directive command queue (consumed flag) admin confirm-gate state machine (pending→confirmed→executed)

Each of these is just "a table + a couple of reducers + clients that poll/subscribe." A traditional stack would need a message broker, a job runner, and careful locking to get the same guarantees.
